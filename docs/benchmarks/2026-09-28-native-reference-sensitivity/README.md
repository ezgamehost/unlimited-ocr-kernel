# Native prefill versus upstream reference configurations

The accepted native BF16 runtime still fails the current logit tolerance against
all three upstream reference configurations. Changing the reference thread count
reduces the number of violations but does not establish parity.

| Reference | Max absolute difference | RMS difference | Violations |
|---|---:|---:|---:|
| Original fixture, ten threads, nine head rows | 0.0001540184 | 0.0000400269 | 24 |
| Ten threads, one head row | 0.0001516342 | 0.0000399475 | 23 |
| One thread, one head row | 0.0001530647 | 0.0000335881 | 9 |

All comparisons check all 129,280 prefill logits at position 276 with
`1e-4 + 1e-4 * abs(reference)`. Top-1 agrees in every comparison. Vocabulary
indices 79354 and 86572 fail against all three references. The original and
ten-thread prefill-only references have identical hidden states; their final
head batch shapes differ. The one-thread reference also changes the decoder
rounding path. See the adjacent reference-thread-sensitivity evidence.

The temporary test-only instrumentation in diagnostic.patch writes native last
hidden states for all twelve layers and final logits to
`artifacts/reference-thread-sensitivity/native-prefill.json`. It does not change
runtime arithmetic. The existing component diagnostic ran successfully, reproduced
the original 24 failures, and exited normally. Its success means the diagnostic
completed, not that the separate parity gate passed. Instrumentation was then
removed. compare.py compares the saved arrays with the frozen reference files;
results.json includes their hashes and per-layer errors.

To reproduce, apply diagnostic.patch, run the ignored
`prefill_logit_component_diagnostic` release integration test with `--nocapture`,
restore the test source, then run compare.py with the project Python environment.
The native snapshot and comparison report refuse overwrite. The reference
snapshots must first be generated by the adjacent thread-sensitivity probe.

This run was on battery and supports no performance claim. Neither runtime
precision nor tolerance changed. The next numerical investigation needs an
independent higher-precision comparison; choosing whichever FP32 reference gives
fewer failures would not resolve the correctness question.
